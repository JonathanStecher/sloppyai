# Repair a rejected visual system

Use this when the user says the redesign still has the same generic layout or
rejects the combined typography, composition and controls. This is a conditional
repair workflow, not a default requirement to redesign every interface. Read with
[product identity](product-identity.md) and [visual quality](visual-quality.md).

## Diagnose the unchanged model

Before drawing another version, describe the current reading order in ordinary
words: what occupies the first screen, what the visitor can do there, how the
product is demonstrated, and what repeats farther down. Record the actual type
roles and action hierarchy too. A list of colour tokens is not this baseline.

In the OFFBEAT worked example, the ordinary and first guided versions both used
a left slogan beside instrument artwork, a three-card catalogue, an explainer,
a two-column planner and FAQs. New colours, a stepped wordmark and clearer labels
improved some details, but the user rejected the shared overall look. The guide
had treated two treatments of that model as sufficiently different alternatives.
This is observed feedback on one example, not evidence of an AI layout category.

Name the failed assumption. It might be that a catalogue needs an introductory
slogan, that each product belongs in a tile, or that every primary action needs
a rounded filled rectangle and arrow. Preserve the required information and
behaviour; reconsider an inferred presentation when it caused the rejection.

## Compare different reading experiences

When the layout itself was rejected, build small alternatives with different
content priorities and spatial relationships. Give each the same offer, actual
content and useful action. A full-width inventory with audition and rental costs
is a different model from an image-led introduction; two palettes on the same
introduction are not. These are examples, not replacement templates.

Compare matched desktop and phone renders, including one useful lower section.
Use a temporary grayscale view to examine emphasis and silhouette separately
from the palette. This does not assess colour quality and need not remove colour
from the delivered product. Ask where the eye starts, how the visitor reaches a
decision and whether the alternative still depends on the rejected arrangement.
Do not count changed pixels or impose a novelty/difference percentage.

For the chosen direction, connect the following decisions to actual content:

- **Typography:** test the product name, a long title, a price, form labels and an
  error at their intended sizes. Compare letter shapes, width, weight, spacing
  and reading rhythm, not just family names. New fonts need usable licences and
  verified loading; an existing or system family can be the strongest choice.
- **Composition:** decide which real content leads, how imagery contributes and
  how density changes through the page. Rebuilding a rejected composition can
  require changing markup. Preserving behaviour does not require preserving its
  boxes, duplicate hero imagery or generated section order.
- **Controls:** design navigation, audition, selection, comparison, form actions
  and recovery as distinct jobs within one visual language. Compare normal,
  focus, hover, selected, disabled and error states. A relevant play symbol or
  familiar button remains useful; removing every icon is not the goal.
- **Overall identity:** make the combination recognisable in the catalogue,
  selected choices, costs and completion as well as the first screen. Check
  spacing, image scale and surface proportions at readable detail size.

Explain the selected relationships rather than naming a mood. More typefaces,
larger branding, a poster layout or unframed rows do not automatically improve
the result. A conventional layout may still be right when the actual problem
was weak execution; demonstrate that through current renders and the brief.

## Calibrate fit before escalating the style

A different silhouette can still feel awkward. In a later OFFBEAT revision, a
large condensed masthead and open inventory changed the earlier page model, but
the user still found the design weird. Difference had been demonstrated; fit and
visual acceptance had not. Do not assume the next concept must be louder,
quieter or more unusual.

Check whether the brand, headline, product imagery and useful actions have natural
proportions for the expected service. Compare actual words and controls at reading
size, with enough context to judge them together. A masthead should earn the space
it takes from the product, and strong display type need not appear in every price,
button and completion state. A well-made familiar control can be the best choice.

If the feedback is broad and repeated, ask one short preference question when it
would resolve the direction, while continuing independent work. Compare a
credible alternative that reflects the user's direction with the same useful
content; do not turn it into a plain wireframe to favour another candidate.
Translate the chosen direction into real content and useful interaction. A music
software direction can lead with actual listening and selection; decorative
waveforms, invented meters or non-working studio controls do not establish fit.
This is an example of grounding the design, not a required music-site template.
Preserve an explicitly approved poster, unusual type or dense composition. This
is contextual calibration, not a new ban on expressive design or a fixed scale,
radius or palette rule.

## Recheck the rejected experience

Compare the revised page directly with the rejected baseline at equal widths,
in colour and with the temporary grayscale aid. State what changed in reading
order, typographic voice, imagery and action treatment, what stayed conventional
for a useful reason, and which weaknesses remain. Recheck the real journey and
protected features. Visual response, functional preservation and user acceptance
are separate outcomes. If the unwanted combined treatment remains recognisable,
record the visual repair as unchanged or failed even when runtime checks pass.

If the coding environment cannot render, retain the failed attempt and request
a concrete host capture: revision/digest, route, widths and required states. Use
returned screenshots as attributed host evidence only after inspecting them.
Their presence does not make a failed launch successful, and source intent is
not a visual review. Keep this step partial until the evidence arrives; do not
silently choose an alternative from code and describe it as pixel-tested.

## Counterexamples and limits

- Preserve an approved brand, a deliberate reference-style match and a useful
  shared component system. A rejection elsewhere does not revoke that acceptance.
- A dashboard can need repeated cards; a shop can need a product grid; a form can
  need an ordinary filled submit button. Judge their execution in context.
- A small alignment or clipping repair does not require alternative concepts.
- A different composition can be less usable. Novelty does not override legible
  prices, truthful content, keyboard access or recovery.
- This guide is a review method, not model-weight training, an authorship
  classifier, a universal taste score or proof that the user will like the result.

Use the existing repair bounds. A user rejection is evidence to revise the design
assumption, not a reason to add endless rules or keep iterating without progress.
